The actual lifecycle mapping is DRAFT → Draft, LOADED → Prepared/Loaded, ACTIVE → Active, SUBMITTED → Awaiting Confirmation, UNDER_REVIEW → Under Review, DISCREPANCY → Discrepancy, CLOSED → Completed/Closed; `cancelled` overrides the display to Cancelled. No new database status was introduced. Date-filtered history can include any selected lifecycle; current trips stay visible independently above it. Without dates, the latest 100 closed trips remain available; choosing a range uses the existing paginated historical query to retrieve older records.

Load counts come from original `trip_load_items`, fetched in bounded batches with deterministic 500-row pagination. They are not inferred from a vehicle's changing current balance and do not claim remaining stock. Vehicle assignment comes from each non-closed trip. Driver assignment/activity comes from the existing `admin_driver_directory` RPC; activity is operational activity, not online presence or Auth last sign-in.

## Shared design and accessibility

- Reused teal/white `Card`, `Button`, `Input`, `StatusBadge`, `OperationForm`, `BsDatePicker`, `BsDateRange`, localization and the existing native `AdminDialog`.
- Dialogs keep focus inside, support Escape, return focus to their trigger and prevent closing while a server operation is pending. Language switching is available inside these dialogs. Fields and controlled HOUSE selections stay mounted while changing language; failed saves retain entered fields for correction.
- Customer type/approval controls use a compact shared layout on admin forms; existing driver forms keep their prior layout. Native select option labels use translated plain strings.
- Shared headings stack actions below the description on narrow screens. Sidebar and navbar remain unchanged.
- Audit records and technical references are available in details rather than main directory cards. New labels have English and Nepali dictionary entries. User-entered names, descriptions and reasons remain literal.

## Authentication review

Authentication, email confirmation, password handling, RLS, approval transitions and trusted-device access are unchanged. The profile-management action adds an existing-profile check to prevent accidental Add Driver overwrites. No new authentication account is created by this UI. Properly approved fixture accounts can sign in through the existing login page; production provider login and mail delivery are not verified by the local adapter.

No specific production login failure was reproduced. Repository findings and a concrete invitation/callback/password-setup/retry plan are in [DRIVER_INVITATION_PLAN.md](./DRIVER_INVITATION_PLAN.md). A server-only Auth Admin service, email/redirect configuration and durable partial-failure handling are additional infrastructure; approval is required before deploying that separate workflow. Supabase credentials are not exposed to the browser and no plaintext passwords were added.

## Remaining issues

1. **Database-level vehicle deactivation protection:** the existing `save_vehicle` RPC does not atomically lock/check open-trip assignments before changing active status. This task blocks the normal UI and server-action paths when an open trip is observed, but a concurrent assignment or direct authorized RPC could bypass that preflight. Review an atomic RPC guard using the same locking order as trip creation before relying on the rule across all clients. No inventory/transaction RPC or migration was changed here.
2. **Driver invitations:** Add Driver still requires a provisioned Auth identity. The separately documented secure invitation workflow is not implemented or deployed.
3. **Shared mobile Admin navigation — resolved in the subsequent 15 October 2026 pass:** the sidebar is now hidden below 1024px and opens from the compact navbar as an accessible modal drawer. See [ADMIN_MOBILE_NAVIGATION.md](./ADMIN_MOBILE_NAVIGATION.md) for the implementation and six tested viewport sizes.
4. **Real devices and production Auth:** tests use actual emulated viewport sizes at default zoom, not physical devices. Live email delivery, production login failures and real-device keyboard behavior require staging/device checks.
