# Secure driver invitation plan

This UI task retains the existing Supabase authentication flow. No Auth users, passwords, confirmation settings, service credentials, Cloud records or RLS policies were changed. The Add Driver dialog links an account already provisioned in Supabase Auth; it does **not** send an invitation. An additional server check rejects creation when that driver profile is already linked, including profiles still at version zero.

## Findings verified in the repository

- `src/app/sign-in/actions.ts` calls `auth.signInWithPassword`; provider failure produces the existing credential/retry message. Inactive admin sessions are signed out. Driver routing depends on their current profile and approval.
- `src/services/auth.ts` and `src/domain/auth/roles.ts` enforce approval and account status. Pending, suspended and rejected drivers cannot perform operational work. Authentication success alone does not grant access.
- Migration `202610120016_driver_approval.sql` links profiles to existing `auth.users` IDs. `save_driver_account` creates pending or approved profiles according to the existing authorized admin policy. `change_driver_status` records reasons and approval metadata. Profile contact edits do not change Auth email or passwords.
- There is no invitation callback, invite acceptance page or password setup page in `src/app`. There is no application call to `auth.admin.inviteUserByEmail`. `.env.example` documents the service-role credential for the seed script only; that entry does not establish an approved runtime invitation service.
- First-time trusted device setup is an online, approved-driver operation. `src/services/trusted-device.ts` uses the existing offline identity guard and encrypted recovery configuration. Linking a profile or sending an invitation must not register an offline device or bypass those checks.
- An email/account can authenticate successfully but still have no profile, pending approval or suspended access. Routing such a user to their account page is intentional. It is not evidence of a broken password login.

No production driver login failure was reproduced during this task. Browser tests use a local Auth adapter and real application SQL/RLS on ephemeral PostgreSQL; they verify application routing and access, not Supabase Cloud password verification or email delivery. Existing sign-in unit tests cover configuration, credential validation, provider failures and account routing. No private account credentials were printed or changed.

## Proposed implementation, requiring approval before deployment

1. Configure a dedicated server-only Auth Admin client with a deployment secret, an approved public site URL, explicit callback allowlist and a tested mail sender. Keep confirmation enabled. Supabase requires invitations to run server-side and the redirect URL to be allowed. See [Supabase users and invitations](https://supabase.com/docs/guides/auth/users), [inviteUserByEmail](https://supabase.com/docs/reference/javascript/auth-admin-inviteuserbyemail) and [redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls).
2. Add an admin-only invitation action accepting name, normalized email, optional phone and required audit reason. Verify the current Auth identity and active admin profile for each request. Keep the privileged client restricted to necessary Auth calls; use the ordinary authenticated client for audited profile RPCs.
3. Use a durable invitation request ID and explicit pending/sent/link-failed/completed states. Serialize duplicate requests and handle provider duplicate-account responses without overwriting existing identities or profiles. Existing accounts should have a separate verified link/retry action. Specify resend rules and rate limits before implementation.
4. Invite through the supported Auth Admin API. Link the returned, verified Auth user ID through `save_driver_account` with approval false. Do not generate credentials in the browser or persist plaintext passwords. Existing profiles must be rejected rather than silently edited.
5. Treat Auth creation/email delivery and profile linkage as separate operations. They cannot share one database transaction. If linkage fails, retain the returned Auth ID and request state for an audited retry; do not invite again, duplicate the account or delete the account as automatic rollback. A small durable request/outbox schema may be necessary and must be reviewed separately.
6. Build invite acceptance and password setup using Supabase's supported invitation token/session handling. Accept only the intended token type and approved destinations, validate the authenticated identity, keep approval pending, and use `auth.updateUser` for password setup. Never log tokens or passwords. Test the callback/template contract against the configured project before deployment.
7. After the driver accepts the invitation, require the existing admin approval action and reason. The driver then signs in online and registers their trusted device through the unchanged device setup flow. Show clear setup steps and access status.
8. Test duplicate emails and requests, already linked users, expired/reused invitations, confirmation, role restrictions, mail/provider failures, partial-link retry, approval, suspension, online login and first-time offline setup. Include a real staging Supabase Auth/email test; the existing local provider is insufficient to claim invitation delivery works.

Suggested files: `src/lib/supabase/auth-admin.ts` (server-only), `src/services/driver-invitations.ts`, `src/app/admin/drivers/invite/actions.ts`, invite/callback/setup routes, a dedicated invitation form, durable request data access and staging Auth tests. No such runtime invitation logic was added by this UI change.

## Operational follow-up

For a reported live login failure, inspect the exact approved account in Supabase Auth, its confirmed-email/account state, matching profile UUID/approval/active status, project configuration and provider logs. For offline initialization, also check the existing recovery-key configuration and trusted-device registration response. Capture redacted error codes and timestamps; keep authentication failures distinct from approval, network and device-setup failures. The generic credential error remains unchanged to avoid exposing account existence on the public sign-in page.
