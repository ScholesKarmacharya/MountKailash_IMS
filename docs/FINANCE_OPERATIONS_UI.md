## Preserved calculations and business behavior

No migrations, database reset, production data writes, accounting RPC changes, permission changes or RLS changes were made. Money calculations continue to use `financeMetrics`, `invoiceTotals`, `invoicePaymentStatus`, `creditStatement`, `creditAging`, `sum`, `cents`, `decimal` and `npr`. Closing totals continue to come directly from `DayReport`; the UI does not recompute or modify archived financial totals.

Payment meaning, signed deposit entries, HOUSE reference values, Fonepay reconciliation, refundable liability, jar FIFO/carry-forward, trip settlement, prepared overnight allocations and immutable closing records are retained. Billing changes still apply through the existing confirmed-company action and leave historical invoice snapshots intact. The driver application's navigation and online/offline runtime remain unchanged.

Payment date/customer/driver/trip filters now consistently scope both lists using existing immutable sale/receipt relationships. Method and disposition filters apply to receipts; the helper text makes that scope explicit rather than inventing invoice status semantics. The overview remains independent of history filters and uses its selected business day. Default selection retains an active closing-review day or the latest recorded day instead of presenting an unspecified zero-sales day when no OPEN day exists.

Current cumulative receivables and deposit liability are clearly labeled. Deposit refund/reversal breakdown displays positive magnitudes from the existing signed ledger, while liability calculations retain the original signed sums. Pending payments are not treated as confirmed paid amounts.

Sync check-in and pending counts are server-recorded telemetry. A review count of zero does not establish that an offline phone has no unsent records. Rejected envelopes, reasons and original payloads remain accessible; no discarded record is silently deleted or posted to finance.

## Limits and remaining concerns

- The existing operational trip dropdown supplies open trips and the latest closed-trip set. Receipt driver filtering also uses existing immutable sale metadata for older trips; a receipt on an older credit-recovery-only trip without that metadata may need additional authoritative read metadata for complete driver filtering. Existing receipts/invoices remain accessible without that filter. No relationship is guessed from the receipt actor.
- Viewport tests do not verify physical devices, Safari, production Supabase Auth or live payment-provider integration. Fonepay remains explicit admin reconciliation.
- Server-confirmed sync reports cannot inspect unreported phone records. The UI explicitly preserves that uncertainty.
- Earlier documented secure driver invitations and atomic database-level vehicle-deactivation protection remain separate follow-ups. This pass does not change authentication or vehicle RPCs.
