README and CI use `--no-shell` to avoid installing the unused headless shell. No application test failures remain in the executed suites.

Docker, Supabase CLI and PostgreSQL are not installed in this environment; `.env.local` and user-supplied demo passwords are absent. The migration, RLS, seed and real session lifecycle therefore still need runtime acceptance on a disposable local Supabase instance. CI includes a database job, but no remote CI run is claimed. Follow README and `SPRINT_0_IMPLEMENTATION.md` to run these checks.

## Coverage and limits

Unit tests exercise allowed/denied roles, disabled identities, missing sessions, forged metadata, profile-query failures, direct service guards, sign-in validation, role redirects, sign-out and Nepal midnight display. Browser tests cover setup messaging, labeled disabled inputs and direct unauthenticated navigation to `/admin`, `/admin/dashboard`, `/driver` and `/driver/home` on both viewports. These tests do not claim to exercise a live authenticated Supabase session.

SQL tests cover driver/admin/disabled profile reads, denied role promotion and business-day writes, required closing metadata and uniqueness across OPEN/CLOSING_REVIEW. The separate authenticated browser suite covers seeded admin/driver redirects, driver exclusion from admin pages, empty dashboards, responsive shells and sign-out. Both suites require local Supabase before their results can be accepted.

Build inspection exposed static redirects when Supabase was absent at build time. The root layout now explicitly forces dynamic rendering, so account checks and runtime configuration are not frozen into build artifacts. Type-check generates Next route definitions first to support fresh checkouts. `next-env.d.ts` is generated and ignored. `AGENTS.md` was generated by Next dev and retained as framework guidance.
