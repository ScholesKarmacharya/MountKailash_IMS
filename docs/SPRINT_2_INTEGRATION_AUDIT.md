# Sprint 2 integration audit — 2026-10-11

The requested physical workflows passed the automated integration audit. Writes were executed only in disposable PGlite PostgreSQL using the application migrations, RPCs, RLS, server actions and browser screens. Supabase Cloud checks used existing records, private Auth sessions and denied driver writes with nonexistent IDs. No Cloud business records were created, migration applied, database reset, RLS disabled, account changed or historical data removed.

## Findings and fixes

1. **Stale delivery quantities after a stock refresh:** reproduced in Chromium before the fix. One device drafted 90 full jars while another posted 40 from a 100-jar load. Refresh showed 60 available but still enabled review of the retained 90. PostgreSQL correctly rejected an oversized save; no negative stock was possible. The form now warns, disables review and withholds the save action until the quantities fit the refreshed balance. Draft quantities remain available for correction. The regression was executed on desktop and phone.
2. **Browser tests could accept a previous save notification:** the global success notification lasts eight seconds. The old helper could proceed before the current action committed. It now waits for the current action response, and delivery assertions poll the actual SQL workspace before replaying the captured request key. Persistence, movement counts and trip states are checked explicitly. Waiting for an entire Next development Flight stream proved unsuitable and was removed.
3. **The Sprint 1 Cloud permission script assumed drivers could read no inventory-related rows:** Sprint 2 intentionally allows assigned products, vehicle balances, trip movements and trip audits. The script now tests warehouse quantities, warehouse locations, manual adjustments and their audit events specifically. Assigned operational reads remain legitimate; warehouse writes remain denied.
4. **Redundant refresh on “Continue with updated data”:** removed the immediate `router.refresh()` before `window.location.reload()`. A single reload still resets the saved form and obtains a new request key. The separate “Refresh stock” action continues to retain an unsaved draft.

No database correction or new migration was necessary. All stock RPCs retain their existing transaction, role, business-day, ownership and idempotency checks.

## Remaining limits before Sprint 3

- **Hosted write acceptance is not claimed.** No customer, vehicle, trip or stock fixture was posted to Cloud. The browser write tests use a test-only Auth/PostgREST adapter and real PostgreSQL application SQL. Repeat the cycle on an approved staging Supabase project for hosted-provider parity and staff acceptance.
- **True simultaneous transaction races are not tested by PGlite.** It uses one connection. Staging must exercise two drivers loading the last stock concurrently, overlapping visit/submit requests and simultaneous duplicate approvals. Reviewed row/advisory locks and sequential retry/rollback tests are evidence, not a substitute for that run.
- **Physical closure is not financial settlement.** Cash/Fonepay/credit selections remain unverified `PENDING_SPRINT3` instructions. Finance journals, allocations, prior-credit repayment, receipts and reconciliation still need Sprint 3 implementation. Confirm deposit, tax, customer-price and correction policies before posting financial records.
- Posted visits remain immutable; there is no authorized posted-visit reversal UI yet. Full offline synchronization, refilling/damage workflows and business-day close remain separate deferred work. Single warehouse and full vehicle unload remain documented provisional choices.

The unit/integration and executed browser checks found no remaining stock-integrity or trip-authorization failure. Complete staging concurrency and hosted write acceptance before treating Sprint 2 as operationally signed off.
